# Особенности написания собственного unsafe API

## 🎯 Главный принцип

**Если функция `unsafe` — она должна явно документировать свои инварианты** — то, что обязан гарантировать вызывающий.

**Инвариант** — это «правила игры», которые разработчик обещает соблюдать, чтобы функция работала правильно.

## 🛡️ Sound API

**Если функция `safe`** — она внутри может содержать `unsafe`, но **снаружи должна быть невозможна никакая комбинация валидных аргументов и состояний, которая приводит к UB**.

Это называется **sound API**. Любое отступление — потенциальный **security баг**.

## 📝 Документация как контракт

В библиотеках с большим количеством `unsafe` принято:

1. Писать раздел **`# Safety`** в doc-комментарии.
2. Покрывать код **Miri**.

**Miri** — экспериментальный интерпретатор для промежуточного представления Rust (MIR), который выполняет код, отслеживая операции с памятью и указателями, чтобы обнаружить **UB** (undefined behavior).

**Документация — это не косметика. Это контракт, без которого использовать `unsafe` правильно нельзя.**

## 📌 Пример: `split_at_mut`

Ваш код — **sound unsafe API**:

```rust
use std::slice;

fn split_at_mut<T>(slice_in: &mut [T], mid: usize) -> (&mut [T], &mut [T]) {
    let len_slice = slice_in.len();

    assert!(mid <= len_slice, "mid: {mid} > len_slice: {len_slice}");

    let ptr = slice_in.as_mut_ptr();

    // SAFETY: мы проверили, что `mid <= len`.
    // - ptr.add(mid) остаётся в пределах аллокации (или на её конце)
    // - два среза не пересекаются: [0, mid) и [mid, len)
    // - оба указателя валидны для T, alignment сохраняется
    unsafe {
        (
            slice::from_raw_parts_mut(ptr, mid),
            std::slice::from_raw_parts_mut(ptr.add(mid), len_slice - mid),
        )
    }
}
```

### 🔍 Почему это sound

| Аспект | Анализ |
|--------|--------|
| **Снаружи** | `safe fn` — вызывающий не пишет `unsafe` |
| **Проверка `mid <= len`** | `assert!` **до** `unsafe` — гарантирует, что оба среза в границах |
| **Непересечение** | `[0, mid)` и `[mid, len)` не перекрываются → нет aliasing UB |
| **Валидность `ptr`** | Получен из `slice_in.as_mut_ptr()` — валиден, выровнен |
| **`ptr.add(mid)`** | В пределах аллокации (или ровно на её конце) |
| **Комментарий `// SAFETY:`** | Объясняет **почему** это корректно |
| **`unsafe` блок** | Минимальный — только вызовы `from_raw_parts_mut` |

**Ключевое:** любая комбинация валидных аргументов (`&mut [T]` + `usize`) **не приводит к UB**. Если `mid > len` — паника, а не UB. Это и есть **sound API**.

### 🧪 Проверка через Miri

```bash
rustup +nightly component add miri
cargo +nightly miri test
```

Miri проверит:
- нет ли out-of-bounds,
- нет ли aliasing,
- нет ли use-after-free,
- нет ли misalignment.

Если тест проходит под Miri — с высокой вероятностью код sound (в рамках покрытия).

### 📝 Что можно улучшить в вашем коде

**1. Добавить раздел `# Safety` (даже для safe-функции — полезно):**

```rust
/// Делит изменяемый срез на два по индексу `mid`.
///
/// # Panics
///
/// Паникует, если `mid > slice_in.len()`.
///
/// # Examples
///
/// ```
/// let mut v = vec![1, 2, 3, 4];
/// let (a, b) = split_at_mut(&mut v, 2);
/// assert_eq!(a, &mut [1, 2]);
/// assert_eq!(b, &mut [3, 4]);
/// ```
pub fn split_at_mut<T>(slice_in: &mut [T], mid: usize) -> (&mut [T], &mut [T]) {
    // ...
}
```

**2. Doc-тест** — пример в `# Examples` автоматически запускается `cargo test`.

**3. Опечатка в имени:** `split_at_mute` → `split_at_mut` (без `e`).

**4. Пробелы перед `;`** — в Rust принято `;` **без** пробела:

```rust
let len_slice = slice_in.len();   // ✅
let len_slice = slice_in.len() ;  // ⚠️ не идиоматично
```

**5. `std::slice::` vs `slice::`** — вы импортировали `use std::slice;`, поэтому можно писать `slice::from_raw_parts_mut` без `std::`.

## 📋 Чек-лист sound unsafe API

| Пункт | Обязательно? |
|-------|-------------|
| `# Safety` в doc-комментарии | ✅ для `unsafe fn` |
| `# Panics` — когда паникует | ✅ если есть `assert!`/`panic!` |
| `# Examples` — пример использования | желательно |
| `// SAFETY:` над каждым `unsafe`-блоком | ✅ |
| Все инварианты перечислены | ✅ |
| Проверки **до** `unsafe` | ✅ |
| Приватные поля для инвариантов | ✅ если нужно |
| Тесты покрывают граничные случаи | ✅ |
| Прогон под Miri | ✅ для библиотек с unsafe |
| Safe-обёртка, если возможно | ✅ предпочтительно |

## 🆚 `unsafe fn` vs `safe fn` с `unsafe` внутри

| | `unsafe fn` | `safe fn` с `unsafe` |
|--|-------------|---------------------|
| Вызывающий пишет `unsafe` | ✅ да | ❌ нет |
| Документирует инварианты | ✅ **обязан** | ✅ желательно |
| Инварианты проверяются внутри | ❌ нет | ✅ да (assert, проверки) |
| Может привести к UB | ✅ да, если контракт нарушен | ❌ нет (если sound) |
| Когда использовать | Когда проверка невозможна | Когда можно проверить |

**Правило:** предпочитайте **safe fn с `unsafe` внутри**, если можете проверить инварианты. `unsafe fn` — только когда проверка невозможна на уровне функции (например, `from_raw_parts_mut`).

## 🎯 Итог

**Sound unsafe API** означает:

1. **`unsafe fn`** — документирует **все** инварианты в `# Safety`.
2. **`safe fn` с `unsafe` внутри** — гарантирует, что **никакие** валидные аргументы не приводят к UB.
3. **`// SAFETY:` комментарий** над каждым `unsafe`-блоком — объясняет **почему** это корректно.
4. **Проверки до `unsafe`** — `assert!`, `if`, проверки границ.
5. **Приватные поля** — чтобы инварианты нельзя было нарушить снаружи.
6. **Miri** — проверяет, что UB действительно нет.
7. **Документация** — это **контракт**, без которого `unsafe` использовать правильно нельзя.

Ваш `split_at_mut` — **пример sound API**: снаружи safe, внутри unsafe, инварианты проверены, комментарий `// SAFETY:` объясняет корректность. Добавьте `# Safety`/`# Panics`/`# Examples` в doc-комментарий и прогоните под Miri — получите **production-grade** unsafe API.
